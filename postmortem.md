# Postmortem

## What went wrong

1. **The repo first shipped a synthetic placeholder as the "golden set".** It was generated by a fallback script because the real
   dataset could not be downloaded in the build environment. A notice file said so, but nothing stopped a run on it. *Fix:* `make run`
   refuses to run while the notice exists; the downloader removes it on success.

2. **Our first results could not be reproduced.** A 54-item early run (mean 4.15) was produced on real-dataset items, while the repo's
   `data/` held different questions under the same ids: `harness/finalize.py` found 54 of 54 rows whose id mapped to a different question.
   Cause: the downloader renumbers ids after shuffling, and nothing recorded which data a run used. *Fix:* each run writes a `.meta.json`
   (dataset hash, prompt hashes, models, git commit), finalize checks ids against the golden set, the old runs were moved to
   `results/archive_unreproducible/` and are not cited, and v1 was re-measured on the frozen data.

3. **Hardware made everything slow and fragile.** Everything ran on a CPU-only laptop with 16 GB RAM. Median generation was about 26 s and judging
   about 47 s per item, so one pass over the 160 items took about 6 hours including crashes, and the bias tests added more time on top.
   This is why the planned second prompt version was **not run**. *Lesson:* time five items before planning the schedule, and budget a hosted
   API or GPU for anything that must be repeated - the cost model shows a hosted evaluation pass costs cents.

4. **Ollama crashed repeatedly, and our scripts did not survive it.** Errors included `500 unexpected EOF`, `model runner has unexpectedly stopped
   (resource limitations)` and a 180 s read timeout, with both models loaded on CPU and swap in use. The first runner kept results only at the end
   of the run and did not retry, so a crash lost work; the timeout error was not even caught. We also accidentally started two runs at once
   (duplicate log lines, same output file), and later two bias-test processes. *Fixes:* rows are saved as each item finishes and the run resumes
   automatically, LLM errors and timeouts are retried with back-off, duplicate rows are removed on resume, the timeout was raised to 600 s, the bias
   tests got the same retries, and long jobs are started detached. The bias test still saves its result only at the end, so one of its runs was lost
   completely and had to be repeated.

5. **Human labelling was done without a team.** The brief expects two team labellers; this was a solo project, so an external friend was the
   second labeller, scoring on paper, and the scores were transcribed. That adds a transcription step (risk of typing errors, mitigated by
   echoing each id next to the score) and means the labellers are not equally trained: agreement was only moderate (numbers in the README).
   We did not pilot-label a small batch together to calibrate the guide first, and we did not drop any items.

6. **Configuration drifted early on.** The first changelog named different models than the README told people to run, so scores could not be tied
   to a model pair. Model names are now part of every `.meta.json`.

7. **Cost was initially only an estimate.** Token usage was not recorded at first; the client now records Ollama/OpenAI usage per call and the cost
   model reports measured tokens.

8. **Process gaps.** The folder started without git and `.gitignore` hid `results/*.jsonl` although per-item results are a deliverable. Both fixed.

## Where the judge fails

All figures below use the 130 items on which the two humans differed by at most 1 point (their rounded mean is the 'consensus'); the items they disagreed on by 2+ points are excluded, which flatters the judge.

- **It is lenient.** On average it scores +0.69 points above the consensus (and +0.81 / +1.23 above the two individual labellers).
- **It misses weak answers.** Humans rated 17 answers 3 or lower; the judge gave 13 of them a 4 or 5 (76.5%).
- **It rarely marks down good answers.** Humans rated 113 answers 4 or 5; the judge scored only 4 of them below 4 (3.5%).
- **Most disagreement is 4 vs 5.** Humans gave 90 answers a 4; the judge gave a 5 to 70 of those (77.8%). A 5 from this judge therefore carries little information.
- **When it does flag low, it is usually right.** It scored 8 answers 3 or lower; the humans agreed on 4 (50.0%) - but it flags very few, so recall is poor.
- **Agreement statistics are depressed by the ceiling effect.** Exact agreement with the consensus is 30.0% and kappa is 0.041, partly because almost all scores sit at 4-5; read kappa together with the counts, never alone.

Bias results (see Results in the README): Position bias (system answer vs the expert reference, both orders, n=20 pairs): 7 of 20 verdicts changed when the order was swapped (35.0%, a large flip rate); 13 were consistent. The judge picked the first slot in 27/40 verdicts (67.5%), i.e. it favours the answer shown FIRST. 0 pairs were skipped (unparseable or LLM errors). Verbosity bias (same answer + one filler sentence, n=20): score rose on 0, unchanged on 20, dropped on 0. 13 of the 20 items already scored 5 and could not rise, so the fairer figure is 0 of 7 items below 5 (0.0%) rose. No strong verbosity effect was detected, but the test is weak because of the ceiling effect.

What we have NOT tested: whether the judge can be gamed by adversarial answers (e.g. confident but wrong text that happens to echo the rubric), and whether stricter rubric anchors or few-shot examples would fix the leniency. Both are obvious next experiments.

## Known limitations of the design

- The position-bias test compares the system's answer with the dataset's **expert reference answer**, not two system answers, so it tests slot
  preference, not preference between two comparable systems. It used 20 pairs only because of time.
- The verbosity test uses one fixed filler sentence and only the test set, and items already scored 5 cannot go up, so it is a narrow probe.
- Judge-vs-human agreement is computed on dev and test together; the test-only figure is the cleaner one (finalize reports both runs separately).
- The judge (gemma2:9b) and answerer (phi3:mini) are different models, which reduces self-preference, but the judge is also small and local.
- The two humans differ in strictness, and one was not part of the team; the consensus set excludes items where they differed by 2+ points.

## What we would do differently

- Freeze and hash the data on day 1, and check result ids against it automatically from the start.
- Time five items with the real models before planning; use a hosted API or a GPU, and never run two jobs against one local model server.
- Write results incrementally and make every long-running script resumable from the beginning, including the bias tests.
- Find the second labeller early and pilot-label about 20 items together to calibrate the rubric before labelling all 160.
- Add stricter score anchors or few-shot examples to the judge prompt (it approves almost everything) and re-measure agreement - this, not a new
  system prompt, is the most valuable next experiment.
